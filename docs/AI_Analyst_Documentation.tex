\section{Overview}

\textbf{AI Analyst} is the investment-committee application of the MZQA equity
platform, carved out to run on its own. It carries all the code it needs; the one
thing it does \emph{not} carry is the market and fundamentals data --- it connects
to a pre-built, read-only PostgreSQL warehouse (the \code{xbrl\_sec} data layer,
schema \code{sec}) produced by the ingestion pipeline documented separately.

The application turns a question --- \emph{``what is this worth, and what should I
expect from it?''} --- into a structured, evidence-anchored answer. It exposes
several ways to run:

\begin{itemize}
  \item \textbf{Single-stock committee} --- the full tribunal plus an
        institutional report for one ticker.
  \item \textbf{Group / industry verdict} --- one relative-value deliberation that
        ranks the constituents of a GICS sector or an ad-hoc set of names.
  \item \textbf{Idea generation} --- a deterministic screener, a natural-language
        (LLM) screen, and a one-click \emph{value $+$ sentiment} scanner.
  \item \textbf{Quant desk} --- a machine-learned return forecast, a forward
        covariance, and portfolio optimization, exposed as its own tab.
\end{itemize}

Three backend packages carry the logic: \code{ai\_analyst/committee} (the tribunal
graph, valuation, and evidence assembly), \code{api} (the REST routers and the
\code{api/quant} modeling layer), and \code{xbrl\_sec} (data access, the
macro-cycle models, and the LLM client).

\section{System architecture}

The frontend is a thin client: it collects inputs and renders results. All
financial logic and every LLM call live in the backend. The backend is stateless
with respect to the application --- its only persistent dependency is the shared
warehouse; user-owned state (custom analyst types, provider API keys) is kept
client-side in the browser.

\section{The investment committee (LangGraph)}

The committee is a \code{StateGraph} over a single \code{InvestmentCommitteeState}
(a \code{TypedDict}). It splits into a \emph{prepare} phase and a \emph{debate}
phase. A deterministic gate runs \emph{before} any LLM, so unanalyzable data never
reaches the agents. If the gate passes, a deterministic engine assembles all the
numbers and the evidence nodes attach context; only then does the dialectical
tribunal argue over --- and tilt assumptions on --- that fixed evidence. The Lead
synthesizes a probability-weighted fair value and decides whether another debate
round is warranted (capped at three).

\begin{keybox}[Why the split matters]
The prepare phase is \emph{provider-independent}: the deterministic packet, the
macro/news/institutional evidence, the data-quality report, and the qlib quant
signals are all computed once. This lets several LLM providers debate the
\emph{same} prepared evidence concurrently, and keeps every figure the tribunal
cites reproducible.
\end{keybox}

\subsection{The data-governance gate (advisory by default)}
Completeness is always a hard stop --- with no fundamentals the engine cannot run.
The accounting-identity DQ check, however, is \emph{advisory by default}: the
committee proceeds and surfaces the findings as a warning. Strict blocking is
opt-in via \code{config.dq\_enforce} (the UI's \emph{strict data-governance}
toggle).

\begin{lstlisting}[language=Python]
def route_data_validation(state):
    if not state.get("is_data_complete"):
        return "terminate_error"                     # unanalyzable -> hard stop
    if get_config(state).get("dq_enforce") and not state.get("is_dq_passed"):
        return "terminate_error"                     # strict mode only
    return "analyze_data"                            # advisory: proceed, warn later
\end{lstlisting}

The HTTP layer mirrors this: it returns \textbf{422} only when the data is
incomplete or strict mode blocked the run; otherwise it returns \textbf{200} with a
\code{dq\_warning} object the UI renders as an amber banner.

\section{The multi-provider LLM layer}

Every agent node routes through a provider-agnostic LLM layer built on a single
registry (\code{llm\_providers.py}, stdlib-only). Five providers are supported and
selected \emph{per request}; the user's API key travels with the request and is
never persisted server-side.

\begin{center}\small
\begin{tabular}{@{}>{\bfseries\color{navy}}l l l@{}}
\toprule
\tabhead{Provider} & \tabhead{Wire dialect} & \tabhead{Notes} \\
\midrule
DeepSeek            & openai    & default provider \\
OpenAI (ChatGPT)    & openai    & \\
Moonshot (Kimi)     & openai    & reasoning model; thinking can be disabled to avoid empty completions \\
Gemini (Google)     & openai    & via Google's OpenAI-compatibility endpoint \\
Anthropic (Claude)  & anthropic & dedicated adapter on the official SDK (no OpenAI-compatible endpoint) \\
\bottomrule
\end{tabular}
\end{center}

Two wire dialects cover all five: the \code{openai} dialect serves
\code{POST \{base\_url\}/chat/completions} with a uniform message/tool shape (a
small capability record captures where sampling params, JSON mode, and the
max-tokens field differ), and the \code{anthropic} dialect is a dedicated adapter.
The layer is used two ways: a \emph{narrative} tier (plain-text theses and the
memo) and a \emph{structured} tier (\code{with\_structured\_output} against
Pydantic schemas for scenario / weight / verdict extraction). A host allowlist is
the security boundary that stops a user-supplied \code{base\_url} from walking off
with the key. Offline / no-key runs fall back to deterministic placeholders, so
every deterministic path remains runnable and testable without any provider.

\section{Screener, ideas, and the group verdict}

The screener filters the US/JP universe on fundamentals (deterministic SQL) and
offers a natural-language screen (LLM $\to$ filters). Three idea sub-features use
the LLM layer differently:

\begin{itemize}
  \item \textbf{Value $+$ sentiment scan} --- one LLM call per name for MD\&A tone,
        on the user's selected provider, blended with the qlib alpha and
        regime-conditioned factor-IC weights into a $0$--$100$ interest score.
  \item \textbf{Prompt screen} --- the prompt$\to$filters translation fans out
        across every keyed provider; each surfaces a candidate set (the per-name
        ``found by'' badges), and the union is ranked once.
  \item \textbf{Group ranking} --- a deterministic quantitative composite
        ($z$-scored P/E, EV/EBITDA, P/B, FCF yield, growth, margins). No LLM is
        needed for the ranking; the LLM only writes the optional narrative, on the
        selected provider.
\end{itemize}

For an industry or a screen, the group endpoint resolves the universe to a capped
ticker set, builds the deterministic composite as a seed, and (when a key is
present) refines it with a single structured verdict that attaches per-name stance
and rationale.

\section{The quant desk}

The quant desk is a lean, in-process integration of \code{qlib}: a cross-sectional
alpha model (return prediction), a factor-structured forward covariance, dual
portfolio optimization (a native optimizer \emph{and} qlib's, selectable at
runtime), and a walk-forward out-of-sample backtest with Fama--French
benchmarking. It is exposed through a \code{/api/quant/*} router and a \emph{Quant}
UI tab, and fed into the committee as the \code{qlib\_signals} evidence node and a
Quantitative Factor Analyst specialist. The mathematics of each model is specified
in the \emph{Quantitative \& ML Models} volume; its engineering integration in the
\emph{qlib Integration} volume.

\section{Setup and running}

The application works on defaults if a local Postgres \code{xbrl\_sec} database is
running and the connection and (optionally) a provider key are configured.

\begin{lstlisting}[language=bash]
cd AI_Analyst

# 1) Backend venv + lean deps
py -3 -m venv .venv
.\.venv\Scripts\pip install -r backend\requirements.txt

# 2) Frontend deps
cd frontend; npm install; cd ..

# 3) Point at the existing Postgres + keys (once; keys can also be pasted in the UI)
setx PGPASSWORD "your-postgres-password"
setx DEEPSEEK_API_KEY "sk-your-key-here"

# 4) Run both services and open the browser
.\start_committee.bat
\end{lstlisting}

A token-free, deterministic smoke test of the whole committee engine (no browser,
no provider) runs the offline path:
\begin{lstlisting}[language=bash]
$env:PYTHONPATH="$PWD\backend"
.\.venv\Scripts\python -m ai_analyst.committee.run --ticker MSFT --offline --no-news
\end{lstlisting}

\begin{notebox}[Ports]
The standalone launcher defaults to backend \code{:8027} and frontend \code{:3027},
separate from the parent platform's defaults. The backend must be started from
\code{backend/} so \code{qlib} resolves; the quant desk pre-warms the alpha
cross-section and the walk-forward backtest at startup, so the first user request
is served from cache.
\end{notebox}

\section{Data dependencies and notes}

\begin{itemize}
  \item \textbf{Shared, read-only warehouse.} The committee reads standardized
        fundamentals, market metrics, prices, GICS classification, 13F ownership,
        macro series, factor loadings, MD\&A, and news from the Postgres
        \code{xbrl\_sec} warehouse (schema \code{sec}). The application never
        writes to it. How that warehouse is built --- the raw-to-standardized
        mapping, the metrics, and the reconciliation --- is the subject of the
        \emph{SEC \& EDINET Metrics Mapping \& Reconciliation} volume.
  \item \textbf{App-owned state.} Deployed analyst types and provider keys live in
        the browser, precisely because the warehouse is read-only.
  \item \textbf{Latency.} A full single-stock committee run is minutes-scale even
        in offline / deterministic mode; group and scan runs are seconds-scale.
\end{itemize}
