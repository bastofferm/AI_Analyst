% ================================================================ 1. Overview
\section{Overview}

\textbf{AI\_Analyst} is the investment-committee feature of the MZQA Equity Terminal,
carved out into a self-contained application that can run on its own. It carries all the
code it needs; the one thing it does \emph{not} carry is the market/fundamentals data —
it connects to the existing, read-only PostgreSQL \code{xbrl\_sec} warehouse produced by
the data pipeline.

The application exposes three ways to run the committee:

\begin{itemize}[leftmargin=1.4em, itemsep=2pt]
  \item \textbf{Single stock} — the full tribunal plus an institutional report for one ticker.
  \item \textbf{Industry (GICS)} — one relative-value verdict ranking the constituents of a
        GICS sector or industry group.
  \item \textbf{AI screen} — a natural-language screen, plus a one-click \emph{Value + Sentiment}
        agent that scans for interesting, cheap stocks and overlays management tone read from
        each name's MD\&A.
\end{itemize}

The frontend is a thin client: it collects inputs and renders results. All financial logic
and every LLM call live in the backend. The backend is stateless with respect to the app —
its only persistent dependency is the shared Postgres warehouse; user-owned state (custom
analyst types) is kept client-side in the browser.

% ================================================================ 3. Setup
\section{Setup and running}

The app works on defaults if a local Postgres \code{xbrl\_sec} database is running and the
\code{PGPASSWORD} and \code{DEEPSEEK\_API\_KEY} user environment variables are set.

\begin{lstlisting}[language=bash]
cd AI_Analyst

# 1) Backend venv + lean deps
py -3 -m venv .venv
.\.venv\Scripts\pip install -r backend\requirements.txt

# 2) Frontend deps
cd frontend; npm install; cd ..

# 3) Point at the existing Postgres + keys (once)
setx PGPASSWORD "your-postgres-password"
setx DEEPSEEK_API_KEY "sk-your-key-here"   # optional; can also be pasted in the UI

# 4) Run both services and open the browser
.\start_committee.bat
\end{lstlisting}

A token-free, deterministic smoke test of the whole committee engine (no browser, no DeepSeek):
\begin{lstlisting}[language=bash]
$env:PYTHONPATH="$PWD\backend"
.\.venv\Scripts\python -m ai_analyst.committee.run --ticker MSFT --offline --no-news
\end{lstlisting}

\noindent\textbf{Note on ports.} The standalone launcher defaults to backend \code{:8027}
and frontend \code{:3027}, separate from the MZQA Terminal defaults.

% ================================================================ 4. LangGraph
\section{The committee workflow (LangGraph)}

The committee is a \code{StateGraph} over a single \code{InvestmentCommitteeState}
(\code{TypedDict}). A deterministic gate runs \emph{before} any LLM, so garbage data never
reaches the agents. If the gate passes, a deterministic engine assembles all the numbers;
only then does the dialectical tribunal argue over — and tilt assumptions on — that fixed
evidence. The Lead synthesises a probability-weighted fair value and decides whether another
debate round is warranted (capped at three).

\subsection{The data-governance gate (advisory by default)}
Completeness is always a hard stop — with no fundamentals the engine cannot run. The
accounting-identity DQ check, however, is \emph{advisory by default}: the committee proceeds
and surfaces the findings as a warning. Strict blocking is opt-in via
\code{config.dq\_enforce=true} (the UI's \emph{Strict data-governance} toggle).

\begin{lstlisting}[language=python]
def route_data_validation(state):
    if not state.get("is_data_complete"):
        return "terminate_error"                     # unanalyzable -> hard stop
    if get_config(state).get("dq_enforce") and not state.get("is_dq_passed"):
        return "terminate_error"                     # strict mode only
    return "analyze_data"                            # advisory: proceed, warn later
\end{lstlisting}

The HTTP layer mirrors this: it returns \textbf{422} only when the data is incomplete or strict
mode blocked the run; otherwise it returns \textbf{200} with a \code{dq\_warning} object the UI
renders as an amber banner.

% ================================================================ 5. LangChain LLM
\section{The LLM layer (LangChain / DeepSeek)}

Every agent node routes through a two-tier DeepSeek layer built on
\code{xbrl\_sec.llm.ChatDeepSeek} (a LangChain chat model). The split exists because the
reasoning model is a thinking-mode model that does \emph{not} reliably emit structured tool
output:

\begin{itemize}[leftmargin=1.4em, itemsep=2pt]
  \item \textbf{Reasoner} — \code{deepseek-reasoner}, called for plain-text narrative
        (\code{llm.invoke(prompt).content}); used by Bull / Bear / Auditor / Lead theses and the memo.
  \item \textbf{Structured} — \code{deepseek-chat} with \code{llm.with\_structured\_output(schema)};
        used for scenario / weight / verdict extraction against Pydantic schemas.
\end{itemize}

Both tiers share a SQLite response cache (\code{setup\_llm\_cache}) and a bounded retry loop.
The whole layer is short-circuited when \code{MZQA\_COMMITTEE\_DISABLE\_LLM=1} or no key is
present, so the deterministic paths remain runnable and testable offline.

% ================================================================ 6. Group
\section{Group committee — relative-value verdict}

For an industry or an AI screen the app runs \emph{one} committee deliberation over a set of
names rather than a full per-stock tribunal $N$ times. The endpoint
\code{POST /api/ai/committee/group} resolves the universe to a capped ticker set via the
existing screener, builds a deterministic composite ranking as a seed, and (when a key is
present) refines it with a single structured DeepSeek verdict.

% ================================================================ 7. Agent
\section{Default agent — value + sentiment scanner}

The AI-screen tab ships a one-click agent (\code{POST /api/screener/agent/value-sentiment})
that surfaces interesting, cheap stocks and overlays sentiment mined from the MD\&A text in
the XBRL filings. A cheap-plus-growing pre-filter (with fixed sanity bounds that drop
mis-scaled warehouse rows) produces a shortlist; management tone is then scored on demand for
each name and folded into a composite interest score.

\section{Data dependencies and notes}

\begin{itemize}[leftmargin=1.4em, itemsep=3pt]
  \item \textbf{Shared, read-only DB.} The committee reads standardized fundamentals, market
        metrics, prices, GICS classification, 13F ownership, macro series, MD\&A and news from
        the Postgres \code{xbrl\_sec} warehouse (schema \code{sec}). The sync path opens the
        connection \code{default\_transaction\_read\_only=on}; the app never writes to it.
  \item \textbf{App-owned state} (deployed analyst types) lives in browser \code{localStorage},
        precisely because the warehouse is read-only.
  \item \textbf{Lean dependencies.} \code{backend/requirements.txt} is trimmed to the committee
        runtime path (no torch / dash / cvxpy); the original superset is kept as
        \code{requirements-full.txt}.
  \item \textbf{MD\&A coverage.} \code{fact\_mda\_sections\_us} currently covers $\approx$47
        companies; Japan is far richer ($\approx$6\,855 rows). The agent degrades gracefully
        where a name has no MD\&A or news.
  \item \textbf{Latency.} A full single-stock committee run is minutes-scale (MSFT $\approx$166\,s
        even in offline / deterministic mode); group and agent runs are seconds-scale.
\end{itemize}
